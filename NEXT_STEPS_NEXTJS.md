## Next.js scaffolding plan

Use the checklist below to scaffold an initial Next.js codebase in this repository. Each step is ordered to keep the repo in a working state at all times.

### 1) Choose project defaults
- **Node version:** Decide on an LTS version (e.g., `node 20`) and record it in `.nvmrc` or `.tool-versions`.
- **Package manager:** Pick `npm`, `yarn`, or `pnpm` and document the choice in the README.
- **App name:** Confirm the project name for `create-next-app` (e.g., `web` or the repo name).

### 2) Initialize the Next.js app
- Run `npx create-next-app@latest <app-name> --typescript --eslint --src-dir --app --import-alias "@/*"` to generate the baseline.
- If this repo should host multiple packages, place the app in a subdirectory (e.g., `apps/web`); otherwise, generate in the repo root.
- Commit the generated scaffold immediately after creation to keep history clean.

### 3) Configure quality tooling
- **ESLint:** Enable `next/core-web-vitals` and add any org-specific rules. Ensure the lint script runs `next lint`.
- **Prettier:** Add a `.prettierrc` and `.prettierignore`; integrate with ESLint if desired.
- **TypeScript strictness:** Enable `strict: true` and consider `noPropertyAccessFromIndexSignature`, `exactOptionalPropertyTypes`, and `noUncheckedIndexedAccess` as future hardening steps.
- **Husky/lint-staged (optional):** Add pre-commit hooks for formatting and linting.

### 4) Add testing and verification
- **Unit tests:** Configure Jest or Vitest for components and utilities; add a simple example test to validate setup.
- **E2E tests:** Enable Playwright with the Next.js preset; add one basic page load test.
- **CI:** Add a workflow that installs deps, runs `next lint`, `next test` (or equivalent), and `next build`.

### 5) Environment and configuration
- Create `.env.example` with placeholders (e.g., `NEXT_PUBLIC_API_BASE_URL`).
- Document how to run the dev server (`npm run dev`) and how to supply env vars.
- Add `.gitignore` entries for `.next/`, `.turbo/`, `node_modules/`, and env files.

### 6) Project structure and DX
- Prefer the `/src` layout (`app/` and `app/api/`) for clarity.
- Add shared directories (e.g., `src/components`, `src/lib`, `src/styles`, `src/app/(marketing)`).
- Set up absolute imports using the `@/*` alias generated by `create-next-app`.
- Configure VS Code settings (`.vscode/settings.json`) for format on save and TypeScript preferences, if the team uses VS Code.

### 7) Content and accessibility starters
- Replace the default homepage with a minimal project-branded landing page that exercises routing, metadata, and font usage.
- Include a global layout with a baseline `<header>` and `<main>` landmarks.
- Add a starter `robots.txt` and `sitemap` if appropriate for production.

### 8) Deployment readiness
- Verify `next.config.js` for the target platform (e.g., `output: "standalone"` for container deployments).
- Add a Dockerfile template if containerization is expected.
- Document the deploy command(s) for the chosen host (Vercel, AWS, Render, etc.).

### 9) Migration and follow-up tasks
- Plan import of any existing UI assets or design tokens.
- Add analytics or feature flagging hooks once platforms are chosen.
- Schedule dependency audits and automated updates (e.g., Renovate) after the scaffold lands.
